# ADR-0001：第一阶段使用 PostgreSQL 持久化文档任务

- 状态：Accepted
- 日期：2026-09-19
- 决策范围：文本型 PDF 上传、解析、重试与删除

## 背景

第一份资料闭环需要 API 快速返回、独立 Worker 解析、进程中断后可恢复、失败可解释且重试不重复写入。项目当前只有一个 API、一个文档 Worker 和 PostgreSQL；尚无需要多队列路由、定时调度或跨服务消费的实测负载。

若此时同时引入 Redis/Celery，文档状态、Celery 投递和结果状态会形成三个一致性边界，还需要 Outbox、broker 运维和额外故障演练。直接在 API 内解析则会占用请求进程，不满足大文件异步处理要求。

## 决策

第一阶段把 `processing_jobs` 作为 PostgreSQL 中的持久业务事实：

- API 在短事务中创建文档与幂等任务记录，随后返回 `202`。
- 独立 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务，并写入租约和尝试次数。
- 进程在完成前中断时，租约到期的任务可再次领取。
- 完成写入使用来源哈希、解析器名称和版本的唯一约束；任务重放不会重复创建版本或页。
- 用户重试创建新的审计任务，但相同重试请求键只对应一个任务。
- PostgreSQL 只保存任务状态和解析正文；原始 PDF 存在私有对象存储。

## 替代方案

1. **API 进程内后台任务**：部署或进程退出会丢任务，且解析会与请求争夺资源，拒绝。
2. **Celery + Redis**：扩展能力更强，但当前增加第二个持久协调边界和运维成本，暂缓。
3. **云托管队列**：适合生产跨服务场景，但会提前绑定供应商，暂缓。

## 后果

优点是任务创建与业务状态原子提交、部署组件更少、失败记录可查询，且 API/Worker 仍可独立扩容。代价是高吞吐下轮询会增加数据库负载，暂不具备丰富的调度、优先级和队列隔离能力。

Worker 领取事务必须很短，解析和对象存储调用不得持有数据库事务。任务查询使用部分索引；轮询频率有明确下限。PostgreSQL 不是用来保存大消息 payload 的，任务只引用稳定 ID。

## 重新评审门槛

出现下列任一情况时评审外部 broker：

- 经测量的任务轮询或锁竞争影响在线查询；
- 需要多种独立优先级、延迟任务或复杂调度；
- Worker 跨服务/跨语言消费，数据库连接成为扩展瓶颈；
- 单一数据库故障域不满足部署目标。

迁移到外部 broker 时使用 Outbox 发送触发消息；`processing_jobs` 继续保存用户可见状态、幂等键和审计结果，broker result backend 不成为事实源。
